# План SVG-ілюстрацій для README заняття gz11

Ілюстрації потрібні там, де пояснюється **процес**, **структура** або **рух даних** —
саме це важко сприймати з суцільного тексту. Нижче — перелік діаграм, прив'язаних до
конкретних розділів README, з описом змісту, щоб їх можна було згенерувати й вставити.

**Загальні вимоги до всіх SVG:**
- Статичні (без анімації), `viewBox`, підписи українською.
- Єдина палітра (нейтральний фон `#f1f5f9`/`#f8fafc`, акценти `#334155`, `#2563eb`, `#0ea5e9`).
- Зберігати у `lessons/gz11-first-endpoints/media/`.
- Вставляти в README через `![опис](./media/назва.svg)` одразу під відповідним заголовком.

## Пріоритет 1 — обов'язкові (найбільша користь)

### 1. `ioc-before-after.svg` — Інверсія керування
- **Розділ:** 1.1. Інверсія керування та впровадження залежностей
- **Що показати:** дві панелі поруч.
  - Ліворуч «Без IoC»: об'єкт `ProductService`, усередині стрілка `new InMemoryProductRepository()`
    (сам створює залежність). Підпис: «об'єкт керує створенням залежності».
  - Праворуч «З IoC»: `ProductService` з порожнім «гніздом» під залежність; збоку контейнер
    Spring подає `ProductRepository` стрілкою ззовні. Підпис: «залежність надають ззовні».
- **Мета:** візуально показати, що саме «інвертується» — напрямок створення.

### 2. `ioc-container.svg` — Контейнер як фабрика бінів
- **Розділ:** 1.2. Bean, контейнер і фабрика
- **Що показати:** великий прямокутник «ApplicationContext (контейнер)». Ліворуч від нього вхід:
  «метадані конфігурації: @Service, @Repository, @RestController». Усередині контейнера — кілька
  «бінів» (коробочки `ProductController`, `ProductServiceImpl`, `InMemoryProductRepository`),
  з'єднані стрілками (контейнер їх створив і зв'язав). Підпис унизу: «читає анотації → створює
  біни → зв'язує → тримає у собі».
- **Мета:** пояснити терміни «контейнер», «бін», «фабрика» однією картинкою.

### 3. `layers.svg` — Багатошарова архітектура
- **Розділ:** 4. Багатошарова організація коду
- **Що показати:** чотири горизонтальні шари згори вниз:
  `web (ProductController)` → `service (ProductService / Impl)` → `repository (ProductRepository)` →
  `domain (Product)`. Збоку — `web/dto` і `service/mapper` як допоміжні. Вертикальна стрілка
  «запит униз, відповідь угору». Пунктиром позначити межі між шарами.
- **Мета:** показати пакети як шари та напрямок залежностей.

### 4. `dip.svg` — Принцип інверсії залежностей (DIP)
- **Розділ:** 4.2. Принцип інверсії залежностей (DIP)
- **Що показати:** у центрі — інтерфейс `ProductRepository` (контракт). Згори на нього спирається
  `ProductServiceImpl` (стрілка «залежить від інтерфейсу»). Знизу дві реалізації:
  `InMemoryProductRepository` (суцільна, «заняття 1.1») та `JpaProductRepository`
  (пунктирна, «Модуль 2») — обидві «реалізують» інтерфейс. Підпис: «сервіс не змінюється
  при заміні реалізації».
- **Мета:** показати, чому заміна сховища на БД не зачепить сервіс.

### 5. `request-flow.svg` — Проходження HTTP-запиту крізь шари
- **Розділ:** 4. Багатошарова організація коду (замінює/доповнює ASCII-схему)
- **Що показати:** горизонтальний потік зліва направо:
  `HTTP GET /api/products` → `ProductController` → `ProductService` → `ProductRepository`
  → (повернення) `ProductMapper: Product → DTO` → `JSON`. Стрілки туди-назад.
- **Мета:** зв'язати ендпоінт із шарами та місцем мапінгу в DTO.

### 6. `rest-resource-endpoint.svg` — Ресурс, URI, метод, ендпоінт
- **Розділ:** 5.1. REST, ресурси та ендпоінти
- **Що показати:** розкласти ендпоінт на складові: великим — `GET /api/products/{id}`,
  з виносками: `GET` = «метод (дія)», `/api/products` = «ресурс (колекція)»,
  `{id}` = «ідентифікатор елемента». Поруч міні-таблиця методів GET/POST/PUT/DELETE
  зі стрілками «читати / створити / замінити / видалити».
- **Мета:** унаочнити анатомію REST-ендпоінта.

## Пріоритет 2 — бажані (покращують, але не критичні)

### 7. `dto-contract.svg` — DTO як окремий контракт
- **Розділ:** 6. DTO як контракт HTTP-API
- **Що показати:** доменний `Product` (усі поля) → маппер → два різні DTO:
  `ProductCardDto` (4 поля, «для переліку») і `ProductDetailDto` (усі поля + images + characteristics,
  «для сторінки товару»). Підкреслити, що назовні йде не Product, а DTO.
- **Мета:** показати, навіщо розділяти домен і контракт API.

### 8. `starter-dependencies.svg` — Що приносить стартер
- **Розділ:** 2.2. Стартери Spring Boot
- **Що показати:** одна коробка `spring-boot-starter-web`, від неї стрілки до набору бібліотек,
  які вона підтягує: `Spring MVC`, `вбудований Tomcat`, `Jackson (JSON)`, `валідація` тощо.
  Підпис: «одна залежність → набір сумісних бібліотек».
- **Мета:** пояснити ідею стартера як «пакета залежностей».

### 9. `embedded-server.svg` — Вбудований vs зовнішній сервер
- **Розділ:** 2.3. Вбудований веб-сервер
- **Що показати:** дві панелі.
  - «Традиційно»: окремо стоїть «Сервер Tomcat», у нього ззовні «вкладають» файл застосунку (`.war`).
  - «Spring Boot»: один самодостатній блок «застосунок (.jar)», усередині якого — «Tomcat»
    як бібліотека. Підпис: «сервер усередині застосунку, запуск однією командою».
- **Мета:** унаочнити різницю підходів і перевагу самодостатності.

### 10. `dev-proxy.svg` — Проксіювання та порт 5173 vs 8080
- **Розділ:** 8.2. Проксіювання запитів (замінює/доповнює ASCII-схему)
- **Що показати:** три блоки: «Браузер» → «Сервер розробки Vite :5173» → «Сервер застосунку :8080».
  Над першою стрілкою `GET /api/products (на :5173)`, над другою — «проксі → :8080». Підпис:
  «у браузері видно :5173, бо запит іде на сервер розробки, а він пересилає на :8080».
- **Мета:** закрити питання «чому в URL 5173, а не 8080» наочно.

## Пріоритет 1 (Spring-механіка) — як працює сам Spring

> Окрема вимога: діаграми мають **пояснювати роботу Spring**, а не лише структуру коду —
> показувати, що саме робить фреймворк «під капотом».

### 13. `spring-component-scan.svg` — Сканування компонентів і створення бінів
- **Розділ:** 3. Запуск застосунку та анотація `@SpringBootApplication`
- **Що показати:** `@SpringBootApplication` у кореневому пакеті `com.ua.amazonua`, від нього
  «промінь сканування» вниз по підпакетах. Класи з анотаціями `@RestController`, `@Service`,
  `@Repository`, `@Component` підсвічені (їх Spring бере), звичайні класи без анотацій — ні.
  Стрілка «знайдені класи → контейнер створює з них біни».
- **Мета:** пояснити, ЯК Spring знаходить і реєструє біни (механізм `@ComponentScan`).

### 14. `spring-boot-starter-application.svg` — Три складові `@SpringBootApplication`
- **Розділ:** 3. Запуск застосунку та анотація `@SpringBootApplication`
- **Що показати:** центральна `@SpringBootApplication` розкладається на три анотації-«шестерні»:
  `@SpringBootConfiguration` (реєстрація конфігурації), `@EnableAutoConfiguration`
  (автоконфігурація), `@ComponentScan` (сканування). Під кожною — короткий підпис її ролі.
- **Мета:** показати, що робить ключова анотація Spring Boot зсередини.

### 15. `spring-autoconfiguration.svg` — Як працює автоконфігурація
- **Розділ:** 1.3. Призначення Spring Boot (або 2.3)
- **Що показати:** принцип «за наявності бібліотеки → Spring сам налаштовує». Зліва умови:
  «є spring-boot-starter-web на classpath». Стрілка через механізм `@EnableAutoConfiguration`.
  Справа результат: Spring автоматично створює `DispatcherServlet`, вбудований `Tomcat`,
  конвертер JSON (`Jackson`). Підпис: «умовна конфігурація: налаштовується те, що є у проєкті».
- **Мета:** пояснити автоконфігурацію як відмінну рису Spring Boot.

### 16. `spring-mvc-request.svg` — Обробка HTTP-запиту в Spring MVC
- **Розділ:** 5.2. Реалізація контролера
- **Що показати:** шлях запиту всередині Spring MVC: `HTTP-запит` → `DispatcherServlet`
  (центральний диспетчер Spring) → «пошук потрібного `@GetMapping`-методу» → `ProductController`
  → повернене значення → `HttpMessageConverter (Jackson)` серіалізує у JSON → `HTTP-відповідь`.
  Підкреслити, що `DispatcherServlet` і конвертер — це компоненти Spring, а не наш код.
- **Мета:** показати, ЩО Spring робить між приходом запиту й нашим методом контролера
  (роль `DispatcherServlet`, маршрутизація, серіалізація).

### 17. `spring-di-injection.svg` — Впровадження залежностей через конструктор у Spring
- **Розділ:** 4.3. Впровадження залежностей через конструктор
- **Що показати:** контейнер Spring тримає готові біни; створюючи `ProductServiceImpl`,
  він «підставляє» в аргументи конструктора потрібні біни (`ProductRepository`, `ProductMapper`)
  стрілками з контейнера. Підпис: «ми не викликаємо `new` — контейнер сам підставляє залежності».
- **Мета:** прив'язати загальне поняття DI до конкретного механізму Spring.

## Пріоритет 3 — опційні

### 11. `startup-sequence.svg` — Послідовність запуску
- **Розділ:** 3. Запуск застосунку та анотація `@SpringBootApplication`
- **Що показати:** вертикальний ланцюжок кроків: `main()` → `SpringApplication.run()` →
  «створення ApplicationContext» → «автоконфігурація» → «реєстрація бінів» →
  «старт вбудованого Tomcat» → «застосунок готовий (:8080)».
- **Мета:** показати, що відбувається під час старту.

### 12. `strict-mode-double.svg` — Подвійний запит у StrictMode
- **Розділ:** 8.3. Чому до одного ендпоінта надходить два запити
- **Що показати:** часова вісь: монтування → демонтування → повторне монтування; під кожним
  монтуванням — стрілка `fetch('/api/products')`. Збоку підпис «лише в режимі розробки;
  у збірці — один запит».
- **Мета:** зняти плутанину з двома запитами.
