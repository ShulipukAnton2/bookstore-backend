Після заняття студент здатен:

Матеріал заняття спирається на офіційну документацію Spring Framework, Spring Boot, Apache Maven, MDN та React (див. розділ «Джерела»).

## 1. Spring, Spring Boot і контейнер інверсії керування

### 1.1. Інверсія керування та впровадження залежностей

![Інверсія керування: без IoC і з IoC](./media/ioc-before-after.svg)

#### Звичайний підхід: об'єкт сам створює те, що йому потрібно

Щоб працювати, один об'єкт зазвичай потребує інших. Наприклад, сервіс товарів потребує сховища товарів. Найпростіший спосіб — створити це сховище власноруч, прямо всередині:

```java
public class ProductService {
    private final ProductRepository repository = new InMemoryProductRepository();
    // ...
}
```

Тут `ProductService` сам вирішує, яку саме реалізацію сховища взяти (`new InMemoryProductRepository()`). Він **керує** створенням своєї залежності. Проблема в тому, що сервіс тепер жорстко прив'язаний до конкретного класу: щоб замінити сховище в пам'яті на сховище з базою даних, доведеться редагувати сам сервіс.

#### Інверсія керування: створення залежностей віддають назовні

**Інверсія керування** (*Inversion of Control, IoC*) означає, що об'єкт **перестає сам створювати свої залежності** і натомість **отримує їх ззовні — готовими**. Слово «інверсія» (перевертання) вказує саме на це: керування створенням об'єктів переходить від самого об'єкта до зовнішньої сторони.

За цього підходу сервіс лише *оголошує*, що йому потрібне сховище, але не створює його:

```java
public class ProductService {
    private final ProductRepository repository;

    public ProductService(ProductRepository repository) { // сховище передають ззовні
        this.repository = repository;
    }
}
```

Хто саме передасть це сховище — вирішує зовнішня сторона. У Spring цією зовнішньою стороною є контейнер (див. нижче).

#### Впровадження залежностей — конкретний спосіб виконати інверсію

**Впровадження залежностей** (*Dependency Injection, DI*) — це конкретний спосіб реалізувати інверсію керування. За офіційним визначенням, DI — це форма IoC, за якої об'єкти визначають свої залежності лише через аргументи конструктора, аргументи фабричного методу або властивості, що встановлюються після створення об'єкта; контейнер впроваджує (підставляє) ці залежності, коли створює об'єкт [1].

Простими словами: «впровадити залежність» = **підставити об'єкту готовий об'єкт, який йому потрібен**. У прикладі вище сховище «впроваджується» через аргумент конструктора.

### 1.2. Bean, контейнер і фабрика

#### Bean

Об'єкти, якими керує Spring, називають **бінами** (*beans*). За офіційним визначенням, бін — це об'єкт, який **створюється, збирається та керується** контейнером IoC [1]. Тобто бін — це звичайний об'єкт вашого застосунку, але створює й зберігає його не ваш код, а контейнер.

#### Чому «контейнер»

**Контейнер** — це частина Spring, яка **створює об'єкти, зберігає їх у себе й за потреби віддає тим, хто їх потребує**. Назва «контейнер» (вмістилище) відображає саме це: усі керовані об'єкти «лежать» усередині нього протягом роботи застосунку, а він стежить за їх створенням і з'єднанням між собою.

Щоб знати, *які* об'єкти створювати та *як* їх з'єднувати, контейнер читає **метадані конфігурації** (*configuration metadata*) — вказівки для контейнера. У нашому проєкті ці вказівки — це анотації на класах (`@Service`, `@Repository` тощо). За офіційним описом, контейнер отримує інструкції щодо того, які компоненти створити, налаштувати та з'єднати, читаючи метадані конфігурації, і в результаті формує **повністю налаштований і готовий до виконання застосунок** [2a].

![Контейнер ApplicationContext як фабрика бінів](./media/ioc-container.svg)

#### Фабрика та `BeanFactory`

Об'єкт, призначення якого — **створювати інші об'єкти**, у програмуванні називають **фабрикою** (*factory*). Контейнер Spring — це фабрика бінів.

У коді Spring базовий контейнер представлено інтерфейсом **`BeanFactory`**. За офіційним описом, `BeanFactory` надає основу для механізму IoC у Spring — тобто саме він відповідає за створення та з'єднання бінів [2b].

На практиці застосунок використовує не голий `BeanFactory`, а розширений контейнер — **`ApplicationContext`**. Він має всі можливості `BeanFactory` і додає зручні для реальних застосунків речі: керування життєвим циклом бінів, публікацію подій, доступ до повідомлень для перекладу інтерфейсу тощо [2b]. Офіційна документація рекомендує використовувати саме `ApplicationContext`, якщо немає вагомих причин вчинити інакше [2b].

Отже, коротко: `ApplicationContext` — це контейнер (фабрика), який під час запуску застосунку читає анотації, створює біни, з'єднує їх між собою й тримає у себе до завершення роботи.

### 1.3. Призначення Spring Boot

Spring Framework надає контейнер і компоненти, але потребує значного обсягу ручного налаштування. **Spring Boot** — надбудова, що автоматизує конфігурацію на основі наявних у проєкті бібліотек (**автоконфігурація**) і надає вбудований сервер застосунків, тож окремий зовнішній сервер встановлювати не потрібно.

![Автоконфігурація Spring Boot](./media/spring-autoconfiguration.svg)

## 2. Збірка проєкту: Maven, стартери та вбудований веб-сервер

### 2.1. Maven і система збірки

**Maven** — інструмент керування та збирання проєктів на Java. Проєкт описується одним конфігураційним файлом — **моделлю об'єкта проєкту** (*Project Object Model, POM*), що зберігається у файлі `pom.xml`. За офіційним описом, Maven будує проєкт на основі його POM і набору плагінів [5].

Maven розв'язує, зокрема, дві задачі, важливі на цьому занятті:

1. **Керування залежностями** (*dependency management*). У `pom.xml` перелічуються потрібні бібліотеки (залежності); Maven автоматично завантажує їх із центрального репозиторію **Maven Central** разом з усіма бібліотеками, від яких вони самі залежать. Копіювати `.jar`-файли вручну не потрібно.
2. **Збирання проєкту** (*build*). Maven компілює код, запускає тести й пакує застосунок у виконуваний артефакт.

Офіційна документація Spring Boot наполегливо рекомендує обирати систему збірки, що підтримує керування залежностями та може використовувати артефакти з Maven Central, і називає Maven однією з двох таких систем [6].

Проєкт містить **Maven Wrapper** — скрипт `mvnw` (для Windows — `mvnw.cmd`), що запускає Maven потрібної версії, навіть якщо Maven не встановлено в системі окремо. Тому всі команди подано у формі `./mvnw ...`.

### 2.2. Стартери Spring Boot

Навіть простий веб-застосунок потребує багатьох узгоджених між собою бібліотек (веб-сервер, обробка HTTP, перетворення об'єктів у JSON тощо). Самостійно підібрати їх сумісні версії — складно. Цю задачу розв'язують **стартери**.

За офіційним визначенням, стартери — це **зручний набір описувачів залежностей** (*a set of convenient dependency descriptors*), які можна підключити до застосунку, щоб отримати всі потрібні технології Spring та пов'язані з ними бібліотеки в одному місці, не шукаючи й не копіюючи вручну окремі залежності [6].

Іншими словами, стартер — це **одна залежність, що підтягує набір інших**, уже сумісних між собою. Офіційні стартери мають однакову схему іменування: `spring-boot-starter-*`, де `*` — тип застосунку [6].

У нашому `pom.xml` підключено стартер:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>
```

Стартер `spring-boot-starter-web` призначено для побудови веб-застосунків, зокрема у стилі REST, на основі Spring MVC; він **використовує Tomcat як вбудований веб-сервер за замовчуванням** [6].

![Що приносить стартер spring-boot-starter-web](./media/starter-dependencies.svg)

### 2.3. Вбудований веб-сервер

Щоб приймати HTTP-запити, застосунку потрібен веб-сервер (контейнер сервлетів). Традиційно такий сервер (наприклад, Apache Tomcat) встановлювали окремо, а застосунок пакували в окремий файл і розгортали **всередині** вже запущеного сервера.

Spring Boot використовує інший підхід — **вбудований веб-сервер** (*embedded web server*): сервер постачається як звичайна бібліотека всередині застосунку (її приносить стартер `spring-boot-starter-web`) і запускається програмно під час старту, усередині виклику `SpringApplication.run(...)`.

![Вбудований сервер проти зовнішнього](./media/embedded-server.svg)

Переваги вбудованого сервера:

1. **Не потрібно встановлювати й налаштовувати окремий сервер.** Для запуску достатньо самого застосунку.
2. **Застосунок самодостатній.** Його можна запустити однією командою (`java -jar ...` або `./mvnw spring-boot:run`); сервер уже всередині.
3. **Однакове середовище всюди.** Версія сервера фіксується залежністю в `pom.xml`, тому на комп'ютері розробника й на промисловому сервері працює та сама версія — зникає клас розбіжностей «у мене працювало».
4. **Зручне розгортання в контейнерах.** Самодостатній застосунок простіше запакувати в Docker-образ (це використано в Модулі 3).

## 3. Запуск застосунку та анотація `@SpringBootApplication`

Клас запуску застосунку:

```java
@SpringBootApplication
public class AmazonuaApplication {
    public static void main(String[] args) {
        SpringApplication.run(AmazonuaApplication.class, args);
    }
}
```

Анотація `@SpringBootApplication` є зручним поєднанням трьох анотацій [2]:

| Анотація | Призначення (за документацією) |
|---|---|
| `@EnableAutoConfiguration` | вмикає механізм автоконфігурації Spring Boot |
| `@ComponentScan` | вмикає сканування `@Component` у пакеті, де розташовано клас застосунку |
| `@SpringBootConfiguration` | дозволяє реєстрацію додаткових бінів та імпорт конфігураційних класів |

![Три складові анотації @SpringBootApplication](./media/spring-boot-starter-application.svg)

Два наслідки, важливі для структури проєкту:

1. **Сканування компонентів** починається з пакета класу застосунку й охоплює його підпакети. Тому клас застосунку розміщують у кореневому пакеті, **над** рештою класів. Офіційна документація прямо рекомендує таке розташування, щоб сканування стосувалося лише вашого коду [3].
2. Виклик `SpringApplication.run(...)` створює `ApplicationContext`, виконує автоконфігурацію, реєструє біни та (для веб-застосунку) **запускає вбудований сервер**.

![Послідовність запуску застосунку](./media/startup-sequence.svg)

## 4. Багатошарова організація коду

Код застосунку поділено на шари за відповідальністю. Кожен шар — окремий пакет.

```
com.ua.amazonua
├── domain/        доменна модель (Product, Characteristic) — без залежностей на фреймворк
├── repository/    ProductRepository (інтерфейс) + InMemoryProductRepository (реалізація)
├── service/       ProductService (інтерфейс) + ProductServiceImpl
│   └── mapper/    ProductMapper (перетворення доменної моделі у DTO)
├── web/           ProductController
│   └── dto/       ProductCardDto, ProductDetailDto, CharacteristicDto
├── exception/     ProductNotFoundException
└── config/        WebConfig, ProductSeeder
```

![Шари застосунку](./media/layers.svg)

Напрямок проходження запиту:

![Проходження HTTP-запиту крізь шари](./media/request-flow.svg)

### 4.1. Відповідальність шарів

- **domain** — моделює предметну область. Класи цього шару не містять анотацій фреймворку й не залежать від способу зберігання чи передачі даних.
- **repository** — відповідає за зберігання та пошук доменних об'єктів.
- **service** — містить бізнес-логіку застосунку.
- **web** — приймає HTTP-запити та формує HTTP-відповіді.

### 4.2. Принцип інверсії залежностей (DIP)

![Принцип інверсії залежностей](./media/dip.svg)

Шари service і web залежать не від конкретних класів нижчих шарів, а від **інтерфейсів** (`ProductService`, `ProductRepository`). Інтерфейс визначає *контракт* — набір операцій без прив'язки до реалізації.

Практичний наслідок: на занятті 1.1 використано реалізацію сховища в оперативній пам'яті (`InMemoryProductRepository`). У Модулі 2 її буде замінено на реалізацію з базою даних **за тим самим інтерфейсом** `ProductRepository`. Класи service і web при цьому не зміняться, оскільки вони залежать від контракту, а не від реалізації. У цьому полягає практична користь поділу на шари.

### 4.3. Впровадження залежностей через конструктор

![Впровадження залежностей через конструктор](./media/spring-di-injection.svg)

Залежності передаються через конструктор, а контейнер підставляє відповідні біни:

```java
@Service
public class ProductServiceImpl implements ProductService {

    private final ProductRepository repository;
    private final ProductMapper mapper;

    public ProductServiceImpl(ProductRepository repository, ProductMapper mapper) {
        this.repository = repository;
        this.mapper = mapper;
    }
    // ...
}
```

У коді застосунку немає виразу `new ProductServiceImpl(...)`. Контейнер сам створює біни, позначені стереотипними анотаціями (`@Service`, `@Repository`, `@Component`, `@RestController`), і впроваджує їх у конструктори — відповідно до визначення DI з п. 1.1. Поля оголошено `final`: залежність встановлюється один раз під час створення об'єкта й не змінюється.

## 5. REST-ендпоінти читання даних

### 5.1. REST, ресурси та ендпоінти

**REST** (*Representational State Transfer*) — це стиль архітектури для побудови розподілених систем; за визначенням, це група обмежень (принципів) проєктування, що забезпечують ефективні, надійні та масштабовані системи. Основна ідея REST полягає в тому, що **ресурс** (наприклад, документ або запис) передається між клієнтом і сервером через стандартизовану взаємодію [7]. Веб-сервіс вважають **RESTful**, коли він дотримується цих обмежень; на практиці HTTP-сервіси, які викликають стандартними веб-засобами, часто називають REST-сервісами [7].

Ключові поняття для цього заняття:

- **Ресурс** — сутність, якою оперує API. У нашому застосунку ресурс — товар.
- **URI** (адреса) — ідентифікує ресурс. Наприклад, `/api/products` — колекція товарів, `/api/products/1` — окремий товар із ідентифікатором 1.
- **HTTP-метод** — визначає *дію* над ресурсом.

**Ендпоінт** (*endpoint*) — це конкретна точка доступу до API, тобто поєднання **HTTP-методу** та **URI**, яке обробляє певний запит (наприклад, `GET /api/products/{id}`).

![Анатомія REST-ендпоінта](./media/rest-resource-endpoint.svg)

Дію над ресурсом задає HTTP-метод. Основні методи та їх призначення (за визначеннями MDN) [8]:

| Метод | Призначення | Приклад у магазині |
|---|---|---|
| `GET` | запитує подання ресурсу; лише читає дані, не змінює їх [8] | отримати перелік або один товар |
| `POST` | надсилає дані на сервер, зазвичай змінюючи його стан (створення) [8] | створити новий товар |
| `PUT` | повністю замінює наявний ресурс переданими даними [8] | замінити всі поля товару |
| `PATCH` | застосовує часткові зміни до ресурсу [8] | змінити лише ціну товару |
| `DELETE` | видаляє вказаний ресурс [8] | видалити товар |

На занятті 1.1 реалізовано **лише ендпоінти читання** (метод `GET`), оскільки сховище поки що наповнюється початковими даними. Методи `POST`, `PUT`, `DELETE` для зміни даних буде додано на наступному занятті.

### 5.2. Реалізація контролера

![Обробка HTTP-запиту в Spring MVC](./media/spring-mvc-request.svg)

Контролер оголошує два ендпоінти читання:

```java
@RestController
@RequestMapping("/api/products")
public class ProductController {

    private final ProductService productService;

    public ProductController(ProductService productService) {
        this.productService = productService;
    }

    @GetMapping
    public List<ProductCardDto> list() {
        return productService.findAll();
    }

    @GetMapping("/{id}")
    public ProductDetailDto getOne(@PathVariable Long id) {
        return productService.findById(id);
    }
}
```

**Анотації веб-шару:**

- **`@RestController`** — зручна анотація, що поєднує `@Controller` і `@ResponseBody`; вона застосовує семантику `@ResponseBody` до всіх методів контролера, тобто значення, яке повертає метод, серіалізується безпосередньо в тіло відповіді [4]. У нашому випадку об'єкти DTO серіалізуються у JSON.
- **`@RequestMapping("/api/products")`** на рівні класу задає спільний префікс шляху для всіх методів [4].
- **`@GetMapping`** — скорочений варіант `@RequestMapping` для HTTP-методу GET [4]. Для інших методів існують відповідники: `@PostMapping`, `@PutMapping`, `@PatchMapping`, `@DeleteMapping` [4].
- **`@PathVariable Long id`** зчитує сегмент шляху `{id}` у параметр методу. Згідно з документацією, захоплені змінні шляху автоматично перетворюються на відповідний тип, інакше постає `TypeMismatchException` [4].

### 5.3. Контракти ендпоінтів

| Метод | Шлях | Призначення | Відповідь |
|---|---|---|---|
| GET | `/api/products` | перелік товарів | масив `ProductCardDto` |
| GET | `/api/products/{id}` | один товар | об'єкт `ProductDetailDto` |

## 6. DTO як контракт HTTP-API

**DTO** (*Data Transfer Object*) — об'єкт, призначений для передавання даних між шарами, зокрема назовні через HTTP-API.

![DTO як окремий контракт API](./media/dto-contract.svg)

У застосунку назовні повертаються не доменні об'єкти `Product`, а окремі DTO:

- `ProductCardDto` — містить лише поля, потрібні для переліку: `id`, `name`, `price`, `imageUrl`;
- `ProductDetailDto` — повний набір полів товару, включно зі списком зображень, описом і характеристиками.

Розділення доменної моделі та DTO має дві причини:

1. **Незалежність контракту API від внутрішньої моделі.** Зміни в доменному класі не змінюють автоматично структуру відповіді, яку бачить клієнт.
2. **Контроль над складом відповіді.** Кожен ендпоінт повертає рівно ті поля, що потрібні відповідному сценарію.

Перетворення доменної моделі у DTO винесено в окремий компонент `ProductMapper`, а не розміщено в сервісі: сервіс відповідає за бізнес-логіку, маппер — за перетворення форматів. Це відповідає принципу єдиної відповідальності (*Single Responsibility Principle*).

## 7. Зберігання даних та початкове наповнення

На занятті 1.1 база даних ще не використовується. Реалізація `InMemoryProductRepository` зберігає товари у структурі `ConcurrentHashMap`, а ідентифікатори видає потокобезпечний лічильник `AtomicLong`.

Початкове наповнення сховища винесено в окремий компонент `ProductSeeder`, що реалізує інтерфейс `ApplicationRunner` і виконується після запуску контексту. Такий поділ також відповідає принципу єдиної відповідальності: репозиторій зберігає дані, сидер — наповнює сховище початковими даними.

Зображення товарів розміщено в каталозі `src/main/resources/static/` і віддаються як статичні ресурси за шляхом `/images/...`.

## 8. Взаємодія клієнтської частини з API

Клієнтська частина (окремий застосунок у каталозі `amazonua-ui`) звертається до API двома запитами: до переліку `/api/products` та до окремого товару `/api/products/{id}`.

### 8.1. Відносні шляхи у запитах

У коді клієнтської частини адреса сервера застосунку **не вказується явно**. Запит оформлено так:

```js
fetch('/api/products')   // а не fetch('http://localhost:8080/api/products')
```

Шлях `/api/products`, що починається з `/`, є **відносним**: браузер добудовує його до того джерела (протокол + хост + порт), з якого завантажено сторінку. Сторінку відкрито за адресою `http://localhost:5173`, тому браузер надсилає запит на `http://localhost:5173/api/products`. **Саме тому в інструментах розробника браузера видно порт 5173, а не 8080.** Запит виходить не на сервер застосунку напряму, а на сервер розробки клієнтської частини.

### 8.2. Проксіювання запитів

Сервер розробки (Vite) налаштовано так, що запити за певними шляхами він не обробляє сам, а **перенаправляє (проксіює) на сервер застосунку**. Налаштування у файлі `vite.config.js`:

```js
server: {
  proxy: {
    '/api':    'http://localhost:8080',
    '/images': 'http://localhost:8080',
  },
}
```

Це означає: усе, що надходить на `/api/...` та `/images/...`, сервер розробки передає на `http://localhost:8080`, отримує відповідь і повертає її браузеру. Перенаправлення відбувається **на боці сервера розробки**, а не в браузері, тому в адресі запиту воно не відображається.

Схема проходження запиту:

![Проксіювання запитів: 5173 → 8080](./media/dev-proxy.svg)

Такий підхід дає дві переваги:

1. **Код клієнтської частини не прив'язаний до адреси сервера застосунку.** У коді лише відносний шлях `/api/products`. У промисловому середовищі (Модуль 3) той самий код працюватиме без змін — там запити за шляхом `/api` перенаправлятиме веб-сервер (nginx). Змінюється лише налаштування проксі, а не код.
2. **Для браузера сторінка й запити походять з одного джерела** (`http://localhost:5173`), тому запит не є міжджерельним. Якби код звертався безпосередньо на `http://localhost:8080`, це було б інше джерело, і до запиту застосовувалися б правила спільного використання ресурсів між джерелами (*Cross-Origin Resource Sharing, CORS*).

На боці сервера застосунку CORS також налаштовано (клас `WebConfig`) — на випадок звернення з іншого джерела, зокрема без проксі.

### 8.3. Чому до одного ендпоінта надходить два запити в режимі розробки

Під час відкриття сторінки в інструментах розробника браузера можна побачити, що запит до `/api/products` виконується **двічі**. Це очікувана поведінка режиму розробки, а не помилка в коді.

![Подвійний запит у StrictMode](./media/strict-mode-double.svg)

Причина — компонент React `StrictMode`, у який обгорнуто застосунок (файл `src/main.jsx`). Згідно з офіційною документацією React, `StrictMode` **лише в режимі розробки** навмисно монтує кожен компонент повторно (монтування → демонтування → повторне монтування) і повторно виконує ефекти, щоб допомогти виявити неправильно написані побічні ефекти [9]. Оскільки запит до API виконується в ефекті (`useEffect`), під час повторного монтування він надсилається ще раз.

Важливо:

- Це відбувається **тільки в режимі розробки** (`npm run dev`). У зібраній версії (`npm run build`) `StrictMode` компонентів повторно не монтує, і запит виконується один раз.
- Подвійний запит нешкідливий для застосунку й не потребує виправлення на цьому занятті.

## 9. Запуск і перевірка

### Вимоги до середовища

Проєкт використовує **Spring Boot 3.4.13** та **Java 21**. Якщо в системі типово задіяно новішу версію JDK, перед запуском слід явно вказати Java 21 через змінну `JAVA_HOME`.

### Сервер застосунку

```bash
cd amazonua
./mvnw spring-boot:run
```

Сервер запускається на `http://localhost:8080`. Перелік товарів: `http://localhost:8080/api/products`.

### Порт 8080 уже зайнято (`Port 8080 was already in use`)

Якщо під час запуску застосунок завершується з помилкою `Web server failed to start. Port 8080 was already in use`, це означає, що порт 8080 уже використовує інший процес (наприклад, попередній запуск застосунку, який не було зупинено, або запуск із середовища розробки). Є два шляхи: звільнити порт або запустити застосунок на іншому порту.

**Крок 1. Знайти процес, що займає порт.**

macOS / Linux:
```bash
lsof -i :8080
```
У стовпці `PID` буде ідентифікатор процесу. Альтернативно, одразу лише PID:
```bash
lsof -t -i :8080
```

Windows (PowerShell або cmd):
```bash
netstat -ano | findstr :8080
```
Останнє число в рядку — це PID процесу.

**Крок 2. Завершити процес за його PID.**

macOS / Linux:
```bash
kill <PID>          # коректне завершення
kill -9 <PID>       # примусове, якщо попереднє не спрацювало
```
Одним рядком (знайти й завершити):
```bash
kill $(lsof -t -i :8080)
```

Windows:
```bash
taskkill /PID <PID> /F
```

> Завершуйте лише той процес, у якому ви впевнені. Переконайтеся, що це справді ваш застосунок, а не стороння програма, яка теж використовує цей порт.

**Альтернатива: запустити застосунок на іншому порту** (не завершуючи наявний процес). Порт можна задати через параметр запуску:
```bash
./mvnw spring-boot:run -Dspring-boot.run.arguments=--server.port=8081
```
або через змінну оточення:
```bash
SERVER_PORT=8081 ./mvnw spring-boot:run
```
У такому разі API буде доступне за адресою `http://localhost:8081`.

### Клієнтський застосунок

Клієнтську частину зібрано на React за допомогою інструмента збірки Vite.

**Передумови.** Потрібен встановлений **Node.js** (версія 18 або новіша). Разом із Node.js встановлюється менеджер пакетів `npm`. Перевірити наявність:
```bash
node -v
npm -v
```

```bash
cd amazonua-ui
npm install
```
Команда створює каталог `node_modules` із бібліотеками. Цей каталог не зберігається в репозиторії й відновлюється командою `npm install`.


**Додаткові команди** (знадобляться на пізніших заняттях):
